그리고 그 해결 방법이 **생각이상으로 간단했다는 내용**이다. 이 부분에서 Gemini에게 계속 질문하여 해결하길 바랬지만 *"구축된 인프라 보안 그룹을 확인해라"*, *"VPC 서브넷 설정이 잘못되었다"*  등등..

그로인해 결론부터 말하자면 **문제해결에 AI를 사용하는것은 비추천** 한다는 말을 하고 싶었다. 물론 AI가 유용하긴한데, **문제를 생각해보고 해결하는것이 나름대로 재미도 있었기 때문**이다.

## #️⃣ **문제: DB연결 실패**

> **문제상황**  
> **1.** DB 연결을 로컬에서 마치고 배포까지 완벽하게 했다고 자부한 **엄준식 씨**.  
> **2.** 그는 배포된 도메인에 접속해 **DB 연결 성공을 확인하고 꿀잠에 들었다.**  
> **3.** 그리고 다음 날 아침, 엄준식 씨를 기다리고 있는 건 무수한 팀원들의 카톡 질타였다.  
> **4.** **"준식 씨.. 화면에 Network Error만 뜨는데요?"**  
> **5.** 그럴 리 없다고 생각한 엄준식 씨가 황급히 **본인의 브라우저로 접속해 보니 너무나 정상 작동을 하는 게 아닌가.** 나한테만 되고 남한테는 안 되는 이 억울한 상황... 과연 어떤 문제가 있던것일까?

### **원인 분석**
> 준식 씨는 AI의 조언만 믿고 약 3시간 동안 AWS 인프라와 씨름했으나, 문제는 전혀 해결되지 않았다..  
> 결국 그는 눈물을 머금고 처음부터 다시 문제를 분석해 보기로 했다.

1. **내 컴퓨터**에서 배포된 도메인으로 접속하면 DB 값들이 잘 보여진다.
2. **팀원들의 컴퓨터**에서 배포된 도메인으로 접속하면 `Network Error`가 나타난다.
3. **네트워크 탭을 열어본 준식 씨는 경악을 금치 못했다.**

### **범인은 바로 '자기중심적 사고' (localhost)**
준식 씨가 겪은 이 기이한 현상의 원인은 바로 `localhost`**라는 주소의 함정** 때문이었다.  

**문제의 코드** `apiClient.js`
```js
import axios from 'axios';

// 백엔드 API의 기본 주소
const BASE_URL = 'http://localhost:8000/api';

const apiClient = axios.create({
  baseURL: BASE_URL,
  headers: {
    'Content-Type': 'application/json',
  },
});

export default apiClient;
```

- **준식씨의 상황 (성공):**
    * 준식 씨의 컴퓨터에는 백엔드 서버가 8000번 포트에서 열심히 돌고 있었다.
    * 브라우저가 localhost:8000으로 요청을 보내면, **준식 씨 컴퓨터 내부**의 백엔드를 찾아가니 당연히 성공한다.

- **팀원들의 상황 (실패):**
    * 팀원 A가 본인의 집에서 배포된 사이트에 접속한다.
    * 프론트엔드 코드가 팀원 A의 브라우저에서 실행되며 `localhost:8000`으로 데이터를 요청한다"
    * 팀원 A의 컴퓨터(localhost) **8000번 포트에는 아무것도 없다.** (당연함, 백엔드 서버는 AWS에 있음)
    * 결국 브라우저는 허공에 삽질을 하다 `Network Error`를 뱉어낸 것..

### **해결방안**
이 문제를 해결하려면 apiClient.js의 **BASE_URL을 상대 경로로 변경**해야 한다.  

또한 `admin/backend/app/main.py` 파일에는 FastAPI 백엔드가 `/api` 라우터를 포함하고 동시에 프론트엔드 파일도 함께 서빙하고 있다. 즉, 프론트엔드와 백엔드 API가 같은 도메인에서 서비스 되기 때문에 `BASE_URL`을 localhost 대신 상대 경로인 `/admin`로 변경하면 된다.

**수정 전**:
```js
const BASE_URL = 'http://localhost:8000/api';
```
**수정 후**:
```js
const BASE_URL = '/admin';
```

> 사실 상대경로 **/api** 로 먼저 고쳤다가 **503에러**가 떠서 이 또한 해결하기 위해 엄준식씨는 눈물을 흘리며 오류를 고쳤지만, 503에러가 떴다는것은 **최소한 DB연결은 성공했다는 뜻으로 만족**했다고 한다..

## #️⃣ **문제: VITE_GOOGLE_CLIENT_ID 설정 실패**

> **문제상황**  
> **1.** 이전 오류들을 모두 해결하고 기고만장해진 **엄준식 씨**.  
> **2.** 그는 이제 **관리자 페이지의 보안 로그인 기능**을 제작하려고 한다 .  
> **3.** 그리고 그는 **Google OAuth 2.0 을 활용**하여 로그인 기능을 완성하였다.  
> **4.** 로컬 테스트 이후 준식 씨는 배포를 마쳤고 관리자 페이지에 접속해보려 하는데..  
> **5.** 배포 사이트에서는 **로그인이 되지 않는다.**  
> **6.** 그리고 콘솔창에는 준식씨가 작성한 오류 코드 **VITE_GOOGLE_CLIENT_ID가 설정되지 않았습니다. .env 파일을 확인하세요.** 라는 에러메세지가 보일뿐..
{: .prompt-danger }

<img src="/assets/img/WTC/open/open_mission_2/오류 메세지.png" alt="오류 메세지">

### **원인 분석**
> 원인은 간단하다. 발급받은 `VITE_GOOGLE_CLIENT_ID`를 **배포사이트에서는 읽지 못하는 것**  
> 그러나 준식씨는 이해할 수가 없었다. 분명 **AWS parameter store** 에 환경변수를 적용했을텐데..

1. 그렇다면 **배포사이트**와 **로컬사이트**의 **차이점** 부터 생각해봐야한다.
  - **로컬 환경의 경우** 폴더에 저장한 .env 파일을 통해 VITE_GOOGLE_CLIENT_ID 를 읽어와 로그인이 가능해진다.
  - **배포 환경의 경우** AWS parameter store 환경변수를 저장하여 VITE_GOOGLE_CLIENT_ID를 읽어와야한다.
2. 그러나 **로그인 로직을 제외**하고 **환경변수를 이용하는 다른 로직들은 정상 상태**. 그렇다면 엄준식씨는 무엇을 놓친걸까..

### **프론트와 백엔드는 구분하자 준식씨..**  
> 그리고 엄준식 씨는 로그인 로직의 폴더위치를 확인하기 시작했다..

이 문제를 해결 하기 위해서는  **'빌드 타임(Build Time)'**과 **'런타임(Runtime)'**의 차이를 알아야 한다.  
문제를 해결한 시점에서의 나는 이 문제를 어떻게 설명해야 잘 적을지 고민했고 비유적 표현과 함께 진행해 보겠다.

- **로컬 환경(내 책상)**
  - 내 책상 위엔 **원고(Code)**와 **메모지(.env 파일)**가 같이 있다.
  - 즉, **그때그때 메모지를 보면서 내용을 확인**한다. 그래서 잘 오류 없이 잘 돌아간다.

- **배포 환경 (인쇄소 → 서점)**
  - **GitHub Actions (인쇄소)**: 여기서 `npm run build`를 실행해서 **dist 파일(완성된 책)**을 만든다.
  - **AWS (서점/책장)**: 완성된 책을 꽂아두고 **손님(브라우저)에게 보여준다.**

**즉 준식씨의 실수는..**  

**AWS**에 `VITE_GOOGLE_CLIENT_ID` 값을 넣어봤자 의미가 없었던 것이다. 이미 **Vite**는 `VITE_GOOGLE_CLIENT_ID` 값 없이 `undefined` 상태로 인쇄를 해버린것이다;;

반면, **백엔드(FastAPI)**는 책이 아니라 **'라이브 방송'**과 같은거다. 방송을 시작할 때(Runtime) AWS에 붙은 메모지를 읽을 수 있기 때문에 정상 작동했던 것

### **해결방안**
원인을 알았으니 해결책은 간단하다. **GitHub Actions가 빌드할 때 환경변수를 주입해야 한다.**  

1. **GitHub Secrets 설정**
  - **GitHub 레포지토리 설정**에 가서 `VITE_GOOGLE_CLIENT_ID` 값을 등록(보안은 철저해야 한다.)
2. **CI/CD 파이프라인 수정**
  - 비유하자면 인쇄기(npm run build)를 돌릴때 `secrets` 좀 쓰라고 말하게 된다.

## #️⃣ **마무리**
