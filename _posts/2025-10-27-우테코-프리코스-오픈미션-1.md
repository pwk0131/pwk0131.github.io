## #️⃣ **서론**
이번 미션에서 핵심으로 제시된 **새로운 시도**라는 조건은 나에게 오히려 하나의 **제약**처럼 다가왔다. 겉보기에는 가볍게 들릴 수 있는 표현이지만, 단순히 새로운 방식이나 기술을 시도하는 데 그치는 것이 아니라, 그 시도를 통해 어떤 배움과 성장을 가져갈 수 있을지 깊이 고민해야 비로소 **의미 있는 시도**가 된다고 느꼈기 때문이다.

라고 생각했지만... 원래라면 인프라 구축을 시도하고 도메인까지 구매하여 **배포한 사이트를 결과물로 제출**한다는 계획이 여러가지 사정이 겹쳐서 주제가 달라졌다. 이후 이어서 서술하겠다.

### 🔵 **계획의 변경: AWS 인프라 vs 서비스 배포**

당시 나의 상황은 다음과 같았다.
- **Plan A (원래 계획)**: AWS를 활용하여 견고한 **인프라 구축 연습**하기
- **Plan B (현실적 판단)**: 당장 눈앞에 닥친 **챗봇 서비스 배포** 일정 맞추기

현실적인 판단하에 챗봇 배포 일정을 선택할 수밖에 없었다. 언뜻 보면 아쉬운 선택 같았지만, 현재 프로젝트 스택을 확인해보니 이는 곧 **새로운 도전**이었다.

| **Project Stack**: `Python`, `FastAPI`

`Java Spring` 에 익숙하기에 이는 완전히 새로운 언어와 프레임워크였다. 그리고 주제변경에 있어 아쉬움은 있었으나, **새로운 기술 스택으로 빠르게(1주) 결과물을 만들어내고 실제 운영 환경까지 배포**하는 경험 또한 인프라 구축 못지않은 좋은 기회라 생각하기로 마음먹었다.

## #️⃣ **기획**

### 🔵 **일정**
> 간략한 계획 | ~11.07 (외부일정) | 11.08 ~ 11.09 (기획) | 11.09 ~ 11.16 (구현) | ~ 11.17 (배포)  |  

> 회고작성은 기능개선 이후

### 🔵 **기능 명세**
관리자 페이지에 필요한 페이지들의 페이지와 API 명세서 또한 내가 작성하였기에 백엔드는 그에 맞게 개발하면 된다.
> **추가사항**: DB 변경 로직

| 구분 | 익숙한 언어 | 사용해야 할 언어&DB |
|------|-------------|-----------------|
| 언어 | Java | Python |
| 프레임워크(B) | Spring | FastAPI |
| 프레임워크(F) | Svelte | React |
| DATABASE | MySQL | MongoDB |

- **사용자 질의 데이터 테이블**
  * AI 챗봇의 성능 개선을 위한 핵심 기능. **사용자의 질문 원문**, **AI의 답변**, **AI 판단 분기점**을 명시한다.
  * 사용자의 질문 원문과 AI의 답변을 타임라인 형태로 조회.
  * 검색 기능을 추가하여, 원활한 **정보탐색 구축**
- **사용자 설문조사 통계 확인**
  * 그룹을 설정하여 학년별(1학년/2학년/3학년/4학년), 대학원생, 교직원, 외부인 으로 나누여 **그룹별 설문조사**를 보여준다.
  * 응답속도, 응답품질에 대한 기능이 추가되어 프론트에도 추가해야 한다.
- **트래픽 조회**
  * 필터를 설정하여 1일(시간별 질문 수), 1주(하루별 질문 수), 1개월(하루별 질문 수), 1년(월별 질문 수) 로 차트를 구별한다.
  * 토근량 조회또한 위 로직과 동일하다.
- **사용 비용 조회**
  * 학생 개발팀 입장에서 가장 민감한 부분인 '운영 비용' 모니터링.
  * API 호출 횟수와 토큰 사용량을 시각화하여 예산 초과를 방지.

- **DB 변경 로직**
  * 배포 전 사용하는 **STG_DB** 와, 실제 사용자 데이터 값을 저장하는 **PROD_DB** , 각각 저장되는 값은 다르므로 관리자 페이지에서 변환시키는 기능을 추가해야한다.

## #️⃣ **앞으로의 회고**
이번 글에서는 프로젝트의 시작과 주제 선정 배경을 다루었다면, 이어지는 회고에서는 **기술적인 도전과 운영 경험에 집중하려 한다.** 구체적인 계획은 다음과 같다.

1. **맨땅에 FastAPI: 관리자 페이지 개발기**
- 익숙한 Spring을 떠나 Python/FastAPI 환경에 적응하며 겪은 시행착오
- 기능 구현 과정에서의 트러블 슈팅(Troubleshooting) 기록

2. **실전 배포 그 후: 일주일간의 보안 강화**
- 실제 운영 환경(Prod) 배포 후 마주한 예상치 못한 이슈들
- 직접 부딪히며 깨달은 보안 취약점과 이를 개선하기 위한 고민들

> 트러블 슈팅에대한 내용이 길어진다면 총 4편의 분량이 될지도 모른다..
